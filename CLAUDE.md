# Project rules for AI assistants

## Architecture gate (mandatory)
- Architecture is documented with SEI **Views and Beyond** in `docs/architecture/`.
- The **Module View** (`docs/architecture/01-module-view.md`) is the quality gate for code placement:
  - If the Module View has an element whose responsibility covers the change, put the code there.
  - If it does not, **stop and escalate to the user** for an architectural decision. Never create new top-level packages under `src/sdlcrag/`, and never change the layering or uses-rules, without approval.
- Uses-rules are enforced by `import-linter` (`[tool.importlinter]` in `pyproject.toml`). `uv run lint-imports` must pass.
- Technology changes (replacing a library in the tech stack) need a new or superseding ADR in `docs/architecture/adr/`.

## OSS building blocks first (hard rule, ADR-0016)
- Never build from scratch what an established OSS library or framework built-in already does. Project code is glue plus business rules (corpus scope, window, license policy).
- Check ADR-0016's building-block map first. If custom code still seems necessary, name the libraries checked and why they don't fit, before writing it. This applies to small glue too (wrappers, hooks, adapters): check the tool's own built-in options first.

## Python / TypeScript boundary (mandatory, ADR-0019)
- **Python** lives only in `src/`, `tools/`, `tests/`. **TypeScript** lives only in `web/`. Pre-commit, pytest and CI reject files on the wrong side.
- The two sides share exactly one artifact: **`contracts/openapi.json`**, generated from the FastAPI response models in `sdlcrag.api`. Never edit it by hand; never import across the boundary.
- `web/` is presentation only. Business rules (access control, license policy, scoring, retrieval, extraction) stay in Python; the browser never decides what a user may see.
- API types and calls in `web/` are **generated by orval** into `web/src/lib/api/generated.ts`. Never hand-write API types, `fetch` calls or axios calls; pages import only from `@/lib/api` (dependency-cruiser and oxlint enforce this).
- Changing the API: edit `sdlcrag.api` → `uv run python tools/gen_api_contract.py` → `pnpm -C web gen:api` → fix the type errors → commit all three in one commit.
- Per-user queries pass the user in the query key (`asUser(user, path)`), so cached data never crosses demo users.
- Web gates: `pnpm -C web check && pnpm -C web build` (API client fresh, `tsc` on TypeScript 7, oxlint, dependency-cruiser). Module rules for `web/` live in `web/.dependency-cruiser.cjs`; a new top-level folder under `web/src/` needs a Module View entry and approval, like a new Python package.
- Toolchain versions are not downgraded to fit a tool (e.g. TypeScript 7 → 5/6). When a tool breaks on a current major, look for its supported option or an alternative, and escalate the choice.

## Acceptance tests (mandatory, ADR-0020)
- Every user-facing acceptance criterion in `docs/acceptance-criteria.md` has a Playwright test in `web/e2e/` whose title starts with its ID (`AC-n`). A new or changed user-facing behavior adds or updates the criterion and its test in the same commit.
- Specs must pass in both modes: `pnpm -C web e2e` (mocked, CI) and `pnpm -C web e2e:live` (real stack). Assert relations, not fixture values. Chat specs that call the LLM are tagged `@llm`.
- Mocked responses use the generated contract types (`web/e2e/support/mock-api.ts`); keep them in step with the API.

## Docs evolve with the code (ADR-0012)
- Diagrams are Mermaid, inline in Markdown. No binary images.
- After code changes, run `uv run python tools/gen_diagrams.py` to refresh `docs/architecture/generated/`. pytest fails if the diagrams are stale.
- A change to runtime flow, deployment, or module uses also updates the matching hand-written view (`02-cc-view.md`, `03-allocation-view.md`, `01-module-view.md`) in the same commit.
- Validate Mermaid with `tools/check_mermaid.sh`.

## Conventions
- Python 3.12, uv, ruff, pyrefly, pytest. Run `uv run pytest && uv run lint-imports && uv run ruff check . && uv run pyrefly check` before committing.
- Configuration only via `sdlcrag.core.config.Settings` (env prefix `SDLCRAG_`). No secrets in code.
- Domain models shared across modules live in `sdlcrag.core.models`.
